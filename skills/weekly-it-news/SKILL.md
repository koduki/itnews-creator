# Weekly IT News — evidence-led presentation authoring

## Purpose
Produce and review technically rigorous, visually communicative Japanese presentations. **Structural authority belongs to the pre-AI decks, 2026-01-25 (21 slides) and 2026-04-12 (27 slides).** The later 2026-09-13 (53 slides) and 2026-10-12 (34 slides) decks are optional **design and explanation refinements**, not a replacement for that original news-show format. Do not imitate the earlier decks' unfinished layouts or reproduce copyrighted third-party screenshots. Prefer the host's native presentation creation/editing capabilities rather than building a new PPTX engine. Explicit user instructions and supplied templates override these defaults.

## Two-stage production when the user intends to polish in PowerPoint

**Phase A — Microsoft 365 Copilot Chat / `weekly-it-news`:** talk through story selection, evidence, technical interpretation and design; deliver a **real editable base `.pptx`**. This is an intentional **BASE DRAFT**, not a final deck, if authentic source visuals or finishing work remain. Put exact sources, relevant capture/visual TODOs and editorial qualifications in notes or unobtrusive source captions when possible; otherwise give a concise separate handoff list in the same conversation. Do not require a Word/JSON intermediate, do not fabricate images and do not call the draft complete when requirements remain.

**Phase B — Copilot in PowerPoint / `itnews-powerpoint-polish`:** user opens that base PPTX; the distinct PowerPoint custom skill reviews and edits the **existing file**, adding genuine sourced images if that host can access them, correcting native diagrams, polishing readability and notes, and doing final QA. There is no automatic transfer of an Agent Builder skill or full conversation memory into PowerPoint. The actual PPTX (plus its notes and any user-shared sources/brief) is the handoff. If PowerPoint also cannot capture a requested source, leave it as an explicitly unfinished requirement rather than using a generated lookalike. This two-stage mode **coexists** with end-to-end Copilot Chat generation for users who want that; select based on the user's request.

## Default workflow — Microsoft 365 Copilot Chat first

**Primary entry point: Microsoft 365 Copilot Chat with this skill installed in its Agent Builder custom agent.** Stay in that chat to research, plan, create, verify and deliver an actual PowerPoint. In Agent Builder, the **Create documents, charts, and code (Code Interpreter)** capability is normally available and can generate downloadable files; check that it is enabled. Use a real PowerPoint generation function in the agent when available. If it is not available but the agent can execute bundled scripts, use `scripts/build_pptx.py` as an optional **standard-library-only PPTX fallback inside Copilot Chat**. It creates editable text and genuine embedded local PNG/JPEG evidence, but has limited layouts and does not fetch images from the Web.

**Second choice, still in Copilot Chat:** the separate dedicated **PowerPoint Agent** can generate a presentation. Custom Agent Builder skills do NOT transfer to it automatically; provide the editorial brief/rules explicitly. **Third choice:** Copilot in PowerPoint, only when the user wants to edit there or Chat output remains blocked. Never require a Word intermediate, external Python environment, separate browser automation, JSON file handoff or a manual app switch as the standard workflow. See `references/copilot-chat-workflow.md`, `references/copilot-native-workflow.md` (optional PowerPoint editor), and `references/production-handoff.md` (optional host switch).

Keep an internal image evidence ledger (exact source, relevance, photographer/publisher, rights, actually embedded yes/no). Web results, links and prose descriptions are not screenshot/photo bytes; the Code Interpreter and skill-script sandboxes cannot directly retrieve outside pages or install packages. For an explicit visual-evidence requirement, use genuinely available image assets or mark it unmet.

## Output contract and capability preflight (mandatory)
**A PowerPoint request requires a genuine editable `.pptx` or verified PowerPoint-native presentation exportable to `.pptx` — not Word, PDF, Markdown or slide-shaped pictures.** A base draft can be delivered for a user-approved PowerPoint polishing phase even with reported missing evidence; do not mislabel it final. Check the current Copilot Chat agent's file creation and Code Interpreter abilities before lengthy research. When PowerPoint creation can run inside the agent, do it **there**. If it cannot, offer the dedicated PowerPoint Agent within Copilot Chat before suggesting another app. Do not imply a separate agent was invoked automatically.

If an essential real screenshot/photo cannot be acquired and inserted, report **"screenshot evidence requirement unmet"**. Do not claim success from URLs alone or AI-generated lookalikes. If PPTX creation is unavailable, report **"PPTX output requirement unmet"**, rather than silently returning Word. Verify file type, slide count, and actual embedded image objects whenever tooling permits; otherwise mark the checks unverified. See `references/copilot-runtime-diagnostics.md` and `references/acceptance-tests.md`.

## Operating principles (mandatory)
1. **Research before slides.** Determine audience, date, topics, desired depth, speaking context, output format and new-versus-edit intent. Infer obvious defaults; do not block on nonessential questions. Confirm news dates, versions, specs, claims and quotations from real sources. Distinguish facts, vendor claims, estimates, opinion and forecasts. None of the four sample decks is automatically a source of up-to-date facts.
2. **Build the original topical rhythm.** Default to *dated cover → concise 今週のトピック list → Topic A: authored news explanation → a purposeful run of relevant official/event and journalistic photo evidence, images from news articles, technical figures, authentic screenshots and contextual reference visuals → Topic B explanation → its evidence sequence → ...*. Add technical comparison, implications or a final summary only when useful for the story. Do **not** mandate chapter divider pages, a fixed three-topic count, a 50-slide investigation, or a cross-topic synthesis. See `references/editorial-structure.md`.
3. **Preserve editorial authorship.** An overview slide should answer *what happened, what changed, why it matters, and the presenter's qualified take* where justified. Don't flatten it to anonymous feature bullets. Explicitly label personal interpretation, doubts, analogies and forecasts as commentary, never as established fact. Source-only pages can follow an explanation slide without artificially inventing a separate thesis for every screenshot.
4. **Choose a visual for its meaning, never for decoration.** For each slide decide whether the best medium is text, native shapes/diagram, editable chart, table, authentic event/UI screenshot, credited journalistic photograph, meaningful diagram or image published within a news article, lawfully reusable external image, or none. Being on an official website is NOT a prerequisite. Explain internally how the visual strengthens the claim. An attractive image with no explanatory value is rejected. Never fill whitespace with stock imagery.
5. **Use editable slide objects where practical.** Use native text, shapes, connectors, tables and charts for authored content. Preserve source screenshots as raster where authenticity is the point. Do not replace factual UI or product photos with AI-generated lookalikes. If the host has no optional visual capability, simplify while reporting the limitation; if the missing capability is a required screenshot or PowerPoint output, stop and report the requirement unmet; never pretend to have browsed, captured, embedded or rendered an image.
6. **Check every cited asset and statistic.** For claims, verify original announcements, documentation, papers, repositories, datasets and reliable reporting. For images, actively seek informative photographs, illustrations and comparison graphics within credible news articles as well as original vendor materials. Record publisher, photographer/creator credit where available, article URL/date, image source and rights/attribution. A citation is not a license: evaluate usage rights and the necessity/amount of quoted material. Crop to the relevant area without changing the meaning; avoid reproducing entire third-party presentations or articles without permission.
7. **Validate before delivery.** Inspect every slide at presentation size (render if the host permits); verify source-to-claim agreement, chart mathematics and units, image provenance, text overflow, contrast, hierarchy, captions, and editable status. Revise failures. If rendering or source checking is unavailable, say which checks could not be performed; never imply a pass without evidence.

## Reference visual identity
- 16:9 widescreen; predominantly white background; editorial red `#C00000` for topic labels, section markers, emphasis, and comparison headers; charcoal near `#1E1E1E` / `#333333` for text; subtle light gray dividers/cards. Use secondary colors only to encode specific semantic categories.
- Japanese sans: prefer `Noto Sans JP` / `Noto Sans CJK JP`, with a portable sans fallback. Maintain a clear hierarchy. The references often contain dense 12–19 pt body text; **improve projector legibility** by reducing text or splitting slides rather than reproducing tiny type. Aim for ~20–28 pt for body text when presentation context permits; dense reference material may use smaller sizes if legible at target output.
- **Primary slide families (early decks):** date-led cover; simple red "今週のトピック" agenda with 3–4 or whatever number of actual news items; one red-headline, plain-language news explainer per item; sequential full- or near-full-slide **genuine** news-reporting photographs, article diagrams/photos, event/announcement screenshots, product screenshots, technical architecture figures and comparative evidence. Put source URLs at least in notes/captions; source-only slides may contain little or no authored text.
- **Optional later enhancements:** red numbered topic cards, chapter breaks, editable side-by-side diagrams, comparative tables, charts and a cross-topic conclusion, only when they improve the narrative. Later examples are not a mandatory layout template.
- Maintain an explicit news-item-to-evidence sequence. A source-only slide must have a clear **parent topic, evidence purpose and provenance** in the storyboard/notes; avoid repeating irrelevant screenshots just to fill pages. Prefer a cropped/annotated screenshot for detailed discussion, but a genuine clean full-screen image is valid when viewing the original matters.
- Make explained-news slides informative rather than generic: a short news summary and one or two technical/contextual implications. Preserve a lively speaker voice without treating editorial reactions as verified facts. Split overcrowded text; don't copy pre-AI alignment defects.

## Visual selection decision tree
- Quantitative **time series** → line chart; ranking/size comparisons → bar/dot chart; precise multi-attribute specification → table; linked components/data paths → architecture diagram; sequence/branch → flow/sequence diagram; physical form or visible UI state → verifiable real photograph or screenshot (including from relevant journalism); events or incidents → credible credited photojournalism; important figure in a news article → actual relevant figure or carefully attributed article capture; original vendor statement or stage demo → appropriately cropped, attributed screenshot; conceptual relationships → native editable shapes; an executive conclusion may require **no image**.
- First verify that the material genuinely exists and is comparable. Never manufacture quantities, timelines, products, UI states, citations, graphs or screenshots; do not convert qualitative judgments into fake measurements. A chart without meaningful data is not an option.
- For each proposed visual assess **claim relevance**, **information gain**, **factual validity**, **provenance/permission**, and **readability** on 0 (fail), 1 (partial), 2 (strong). Prefer visuals scoring at least 8/10; **factual validity or provenance = 0 is a hard reject**. Numbers are a review heuristic, not proof. Use a verbal rationale, not a fabricated score, when evidence is incomplete. Improve or remove rejected visuals.
- If source data are fundamentally not comparable, choose explanatory shapes or a caveated table rather than implying quantitative comparability.

## Source, screenshot and chart rules
- Source research: prefer primary factual records for technical assertions while treating reputable reporting as a first-class source of informative photographs, comparative graphics, article figures and independent commentary. Choose visuals by relevance, accuracy and traceable rights, not by an official/nonofficial binary. Cross-check surprising assertions. Record event date separately from article date and deck date. Mark predictions explicitly.
- Web screenshots: capture an actual news article/page when its layout, quote, headline or on-screen state matters. If the useful content is a photograph or diagram *within* an article, prefer that actual image over an unreadable full-webpage screenshot when authorized. Record article publisher and URL, publication/capture date, photographer/creator credit and rights; crop responsibly. Never treat an AI illustration as a genuine product UI, keynote slide, or website screenshot.
- Tables: appropriate for exact multi-attribute comparisons; consistently format values and units, show missing values as unknown rather than assuming zero, distinguish reported specs and inferred specs. Reduce the number of columns before shrinking text.
- Charts: use source numeric data with clear units, period, sample, axis baseline and methodology. Check accuracy and denominators, avoid misleading cropping/dual axes, distinguish measured vs projected, and cite the dataset. Prefer editable native charts.
- Diagrams: ensure meaningful node types and arrow directions; use legend where necessary; mark conceptual diagrams as '模式図'. Use native shapes/lines, not screenshots of arbitrary generated pictures.
- Never invent sources or claim source permissions were verified if the platform cannot inspect them. Flag unverifiable material and replace with defensible textual or native visual alternatives.

## Delivery workflow
1. **Intake and evidence ledger**: audience, date, topic list, input links/files, evidence status, unresolved gaps.
2. **Outline/storyboard by news item**: build topic groups, each with one factual editorial overview and zero or more **evidence-only** slides explaining what the audience should notice. A complete independent thesis is not required for source-only slides. Include asset URL, verification state and reason for inclusion. See `templates/slide-plan.md`.
3. **Construct with host-native presentation capabilities**: when PowerPoint is requested, produce an actual `.pptx` or a verifiably PowerPoint-native file exportable to `.pptx`. A `.docx`, PDF or Markdown draft is NOT an acceptable final substitute. If the host cannot produce PPTX, explicitly report blocked delivery rather than silently changing format. Prefer editable shapes and create the slide families above. Do not assert identical rendering across ChatGPT and Microsoft Copilot.
4. **QA pass and revisions**: verify the requested PPTX format and that documentary images were *actually embedded* rather than merely linked. If real evidence images were requested yet none were inserted, mark that requirement unmet. Perform the checks in `references/quality-gates.md`; inspect rendered slides where supported. Rework low-value visuals and overcrowded slides.
5. **Deliver**: only verified `.pptx` or exportable PowerPoint-native presentation when PowerPoint is requested; short summary of slide count, key findings, source coverage, chosen diagrams/charts/screenshots, editability, and any limitations or unresolved checks. Include an attribution/evidence log as notes or a source appendix for nontrivial external claims/assets.
